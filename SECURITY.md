# Security implementation and deployment

Updated 2026-10-06 (Step 9; revised after the deployment approvals: v1 endpoints retired, Redis TLS required, log redaction extended). These controls protect the current anonymous itinerary planner. It has no accounts, passwords, session cookies, uploads, or private saved itineraries. Account authentication, password hashing, ownership checks, database public keys, and row-level security become required when those features are introduced; SQLite is a server-only place cache today.

## Implemented controls

- **Accepted temporary risk (product manager, 2026-10-07):** for the closed prototype on Railway Hobby the server key has **no outbound-IP restriction** (Hobby has no static egress IP). It stays API-restricted to Places API (New) and Routes API and lives only in Railway secrets. Risk: a leaked key could be used from anywhere against those APIs, billed to our account. **Mandatory review before any public launch:** re-decide the IP restriction (Railway Pro static IPs or equivalent), rotate the key, and re-check quotas and usage.
- Server keys stay in ignored environment files or platform secret storage. Browser code receives only a separate public Maps JavaScript key. Never place a server key in any `NEXT_PUBLIC_*` variable.
- Strict request schemas reject unknown fields, invalid coordinates, blank/oversized strings, dates outside supported bounds, and excessive visit durations. Requests are limited to 12 stops and 16 KiB; chunked requests are counted too. Body reading has a ten-second total deadline and compressed bodies are rejected.
- The v1 endpoints (`/api/plan`, `/api/optimise`, `/api/refresh-leg`) were retired on 2026-10-06; only `/healthz` and `/api/v2/*` are served (tested). Per verified client IP (unchanged values): v2 planning (`/api/v2/plan` and `/api/v2/plan/stream`) shares one 10/minute + 50/day allowance; v2 refresh and v2 comparison each have their own allowance with the same existing values. City/place suggestions and selections share one combined 30/minute + 100/day allowance (D36; counting selections in it is an interim choice pending a product decision). Forwarded IPs are trusted only when the connection peer is listed in `TRUSTED_PROXY_IPS`; the chain is read right to left and the first untrusted hop is the client (more than 16 entries or malformed values fall back to the peer). Whitelist exemptions cannot be spoofed using an untrusted forwarded header. On Railway no trusted proxy range is published, so until the proposed client-IP integration (DEPLOYMENT_PLAN.md §7) is approved and implemented every visitor shares one identity.
- Every actual outbound Google call (Autocomplete, Place Details, Compute Routes; Text Search was removed with v1) consumes a shared daily budget (2,000 by default) before it is sent, including unsuccessful or cancelled calls. Storage failures block calls (fail closed). Each admitted call is also recorded by kind in an accounting seam (`app/core/provider_accounting.py`) for later per-SKU controls; monthly free-tier enforcement is deferred and is not implemented. The budget limits anonymous automation and provider spending; it is not proof of a human user, a dollar cap or a free-tier guarantee. Provider console quotas are also required.
- Request admission (20/process), provider concurrency (20/process), provider queue deadlines, and solver concurrency (2/process) bound resource use. Solver work runs off the event loop with a time limit no longer than the remaining operation deadline; its slot is released when the worker thread ends. Planning, refresh and comparison share one 60-second deadline per operation that bounds every in-flight provider await; streamed operations stop on client disconnect and release capacity. Each open stream holds one admission slot for up to 60 s; the experimental exhaustive four-stop stream (2026-10-08) has its own 240-second deadline, so it can hold a slot for up to 240 s, shares the comparison rate-limit scope and is capped at 72 routing calls per run. Multiple replicas require capacity planning as these caps are per process.
- SQL uses parameters. The persistent Places cache (D38) stores only `place_id`, latitude, longitude and fetch time — no names, types, opening hours, addresses or search text. Rows expire one cleanup interval before 30 days after fetching (reads never extend expiry) and are deleted at startup and hourly. The legacy rich cache is migrated on first use (permitted fields only), dropped, and the file VACUUMed with secure_delete. Cache files use mode 0600 in a 0700 directory. Production keeps this cache in the container filesystem only (no volume, approved 2026-10-06): each redeploy clears it, and there are no volume backups or snapshots. This does not remove storage-security considerations: while the container runs the file sits on the host's disk (encryption at rest not documented by the host), and anyone with shell access to the service can read it. Correctness never depends on it — planning re-verifies places with Google, and a missing, unreadable or failing cache is a miss. If a volume is ever introduced, use a private encrypted volume and remove earlier backups/snapshots according to retention policy. An older deployment may still hold the legacy rich cache; delete it when decommissioning. Rich place details are fetched per operation and kept in memory only.
- React renders user content as text. Browser scripts use a fresh CSP nonce per response; production script policy has no unsafe-inline or unsafe-eval. Inline styles remain enabled for Google Maps. Security headers prevent framing and MIME sniffing, restrict referrers, and disable response caching. API docs and schema endpoints are disabled; developers may generate the schema offline with `app.openapi()`.
- API validation responses omit submitted values and unknown field names. Unexpected failures return a generic 503 (`service_unavailable`), or a generic `internal_error` stream event, with no exception text. Provider bodies/exception text and request payloads are excluded from application logs. Health checks omit environment details.
- Logging (Step 9, D46): one JSON line per v2 operation on stdout (`routewright.metrics`): operation, transport, bounded outcome/failure categories, elapsed time, stop count and provider-call counts by kind. It never contains place names/IDs, coordinates, travel dates, IPs, operation IDs, plans, payloads, secrets or provider text; comparison savings are not logged and completed comparisons are one category until permitted use is confirmed. Uvicorn runs with `--no-access-log --ws none`; library loggers that can carry a client address (slowapi's rate-limit warning, uvicorn's WebSocket handshake lines) pass through an address-redacting filter (`app/core/logredact.py`; tested with a real limiter and a real uvicorn server). Retention is the hosting platform's log retention; Railway documents 7 days (Hobby), 30 days (Pro), up to 90 days (Enterprise) — the project's actual plan must be confirmed. Railway's own HTTP logs record client IPs (`@srcIp`); this is outside the application's control and must be covered by the privacy policy and access controls.
- Dependencies are updated and locked. Python installs verify package hashes. CI blocks Python vulnerability findings, runtime npm vulnerabilities, and new high/critical frontend development findings. Weekly CI repeats scans. Secret scanning covers full Git history and source files, with findings redacted.

## Required production configuration

1. Provision a Redis instance reachable over TLS; set `RATE_LIMIT_STORAGE_URI` on every backend replica to the same `rediss://` database (approved 2026-10-06; no plaintext exception — production refuses `redis://` and URLs that disable certificate or hostname verification, without echoing the URL). Railway's Redis template offers no TLS; the proposed provider is Upstash (TLS always on; DEPLOYMENT_PLAN.md §7). The TLS path was verified locally with the existing client and limiter: plaintext, an untrusted CA and a mismatched hostname are refused. Rate-limit keys currently contain raw client IPs (TTL up to one day); hashing them is proposed with D-1. The backend also refuses production startup with memory storage or an unavailable store. Do not evict/flush rate-limit keys during normal operations. Redis connect/read operations have two-second timeouts; add infrastructure health alerts.
2. Set `APP_ENV=production`, `GOOGLE_MAPS_API_KEY`, and `ALLOWED_ORIGINS=https://your-frontend-domain`. Configure only the real HTTPS frontend origins. CORS does not authenticate callers: this API is intentionally public.
3. Configure `TRUSTED_PROXY_IPS` with the actual ingress connection peers/CIDRs. The ingress must replace or safely append `X-Forwarded-For`; block direct access bypassing it. Uvicorn runs with `--no-proxy-headers` so the application sees the actual peer. Leave trust empty until the provider's topology is verified. `TRUSTED_PROXY_COUNT` is obsolete and rejected.
4. Set frontend `NEXT_PUBLIC_API_URL=https://your-backend-domain`. Enforce HTTP-to-HTTPS redirects at the ingress for both domains. After verification enable backend `HSTS_ENABLED=true` and frontend `SECURITY_HSTS_ENABLED=true`. TLS termination belongs to the ingress; the application cannot prove it is enabled from local code.
5. Create separate Google keys. Restrict the browser key by website referrer and Maps JavaScript API; restrict the server key to Places API (New) and Routes API **and** to a verified server egress IP — required before deployment (approved 2026-10-06); on Railway this needs Pro's Static Outbound IPs, so deployment is blocked pending that cost decision (DEPLOYMENT_PLAN.md §6). Railway's IPs may be shared with other customers: the restriction stops use of a leaked key from elsewhere on the internet, not from co-tenants on the same IP, nor from a compromised backend, and it is not a spend limit. Set Google quotas, billing alerts, and a provider budget appropriate to your traffic; none of these guarantees zero charges, and monthly free-tier enforcement is deferred. Never share keys in chat. Rotate any previously exposed key before rewriting Git history; history cleanup requires coordination with collaborators.
6. Keep the SQLite cache ephemeral in the container (no volume; the image runs as non-root). If persistent storage is ever approved, use a private encrypted volume and restrict backups and retention. Start the backend with a restrictive umask (Docker does this). Monitor generic failure/capacity metrics without recording locations or submitted queries.

Local checks cannot verify these platform settings or live key restrictions. The browser smoke test uses no Maps key, so live Google Maps loading under CSP remains a deployment check. Locally (2026-10-06) the image ran as non-root, served `/healthz`, and its application logs contained no client IPs; shared-Redis tests passed against a disposable local Redis; 429 and WebSocket log paths were verified free of client IPs. All must still pass in the deployment environment before release.

Update to a patched dependency when available; do not extend the exception without reassessing exposure. ## Verification commands

From `backend`: install `requirements-dev.lock` with `pip install --require-hashes -r requirements-dev.lock`, then run `python -m ruff check .`, `python -m ruff format --check .`, `python -m mypy app`, and `python -m pytest -q`.

Shared-store tests: set `SECURITY_TEST_REDIS_URL` to a disposable Redis database (they flush it), e.g. `redis://127.0.0.1:6390/15` on a throwaway `redis:7.4-alpine` container; CI provides one.

From `frontend` on Node 22.13+ (22.x) or Node 24+: run `npm ci`, `npm run type-check`, `npm run lint`, `npm run test:unit`, `npm run check:types-drift`, `npm run security:audit`, then build with a fake server key present — `GOOGLE_MAPS_API_KEY=<probe> NEXT_PUBLIC_API_URL=https://api.routewright.invalid npm run build` — and run `SECURITY_BUNDLE_PROBE=<probe> npm run security:bundle` (fails if the server key or key-shaped strings are bundled). Install Playwright Chromium, then run `npm run security:smoke` and `npm run test:e2e` (mocked API; no Google quota).

See [PRODUCTION_VERIFICATION.md](PRODUCTION_VERIFICATION.md) for checks that need the deployment or live provider calls.
